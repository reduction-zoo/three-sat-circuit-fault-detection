# Independent review of round 001

**Decision: revise.** The Boolean reduction and decoder are correct for the executions they can perform, and the result is a useful reconstruction of a classical fault-detection hardness mechanism. The present executable forward map is not total on all legal finite inputs, and the proof's claimed polynomial bit bound does not follow from its stated estimate. Both issues are local repairs; the gadget and the prepared evidence need not be restarted.

## Correctness

For every legal source formula, `algorithm.py` builds a topologically ordered fan-in-two AND/OR/NOT circuit. Each literal and clause has the intended value, including repeated literals and the empty conjunction (`z OR NOT z`). The sole designated/output wire computes `w=z AND φ(x)`. A fault stuck at `b` on that observed output is detected exactly when its fault-free value is `1-b`. Setting `z=0` detects stuck-at-1; stuck-at-0 has a test exactly when `φ` is satisfiable. Thus an unsatisfiable source gives the target's valid `NO-SOLUTION`, and a satisfiable source gives complete two-entry target outputs. Every valid complete output, in any order and with any detecting vectors, has a stuck-at-0 entry whose first `n` bits satisfy `φ`. The implemented `extract` at [algorithm.py lines 40–47](../../work/algorithm.py) selects that entry. It reconstructs the same wire ID deterministically; no solver or random choice occurs in either map. These arguments establish legality, nonempty answer sets, and recovery from **all** valid outputs, subject to the executable issue below.

The prepared [check.py](../../work/check.py) invokes both maps in separate processes, exhaustively solves each small target instance, validates each generated target answer, and checks recovered source membership against a Z3 source oracle. The separate [verify.py](../../work/verify.py) uses exhaustive Boolean source assignments and its own target simulator. I inspected those loops and their [reported results](../../work/verification.md): 115 instances/201 target outputs and 123 instances/243 outputs respectively, covering satisfiable, unsatisfiable, and alternate complete test sets. I did not repeat either suite; finite evidence cannot prove the unrestricted theorem.

**Executable totality failure.** The legal source `{"n":10^4300,"clauses":[]}` has a 4,301-digit numeric field and a short valid target description under the specified count-based circuit encoding. The real CLI at [algorithm.py line 52](../../work/algorithm.py) exits before construction because Python's default integer-string conversion limit is 4,300 digits. The same limit would also affect writing a sufficiently large numeric target field. [check_large_input.py](check_large_input.py) supplies this source as JSON, calls the real CLI under `uv run python`, and checks the target's input count. It currently fails with `ValueError: Exceeds the limit (4300 digits) for integer string conversion`. The source contract permits arbitrary nonnegative binary-encoded `n` and imposes no 4,300-digit bound, so this is a counterexample to the required total forward map. Repair the JSON numeric read/write path for arbitrary finite legal integers, then rerun this targeted check.

**Bit-complexity proof gap.** [proof.md line 9](../../work/proof.md) says construction time and output length are `O((n+m) log(n+m+2))`, “hence polynomial in input length.” That inference lacks the premise `n=O(|x|)`, which is false when `n` is encoded numerically: an empty-clause formula may name exponentially many unused variables. This is a proof gap, not a lower bound against the algorithm. At most `3m` distinct negative literals are used, so there are at most `6m+O(1)` gates. Each written wire index takes `O(log(n+m+2))` bits. A suitable forward size and time bound is polynomial in `m`, `log(n+1)`, and the source length (for example `O((m+1) log(n+m+2)+|x|)` output bits, with polynomial-cost integer arithmetic). Recovery's circuit reconstruction has the same bit bound; on a complete target output, copying the `n` recovered bits takes `O(n)`, but that output already explicitly contains at least `n+1` input bits, so `n=O(|y|)`. On `NO-SOLUTION`, recovery returns the fixed string. Revise the cited paragraph with these bounds, including arithmetic and the distinction between `n` and its encoding length.

## Novelty

Primary literature checked 2026-09-25: [Ibarra and Sahni, *Polynomially Complete Fault Detection Problems* (1975)](https://www.cise.ufl.edu/~sahni/papers/faultDetection.pdf), Section II's P4 definition (printed p. 243), Theorem 3.4(1) and proof (printed p. 248), and Theorem 3.5 Case 4 (printed p. 248). Theorem 3.4 explicitly uses the equivalence between detecting both output-line polarities and a nonconstant circuit function. The paper frames hardness through 3-DNF tautology and decision/test-set tasks; it does not provide this repository's particular JSON construction and total 3-CNF search decoder. The [upstream issue](https://github.com/CodingThrust/problem-reductions/issues/919) already describes the direct formula-output stuck-at-0 equivalence, though that description does not settle the fixed both-polarities target. Consequently the mathematical hardness mechanism is known, while this explicit `z` gating and decoder constitute a reconstruction for the fixed contract, not an established new complexity theorem. Coverage beyond the cited original paper and upstream issue remains unassessed; no claim of first use of this simple gating device is supported. The fixed question explicitly accepts a published reconstruction.

## Significance and cost

The concrete contribution is a complete, executable bridge from 3-CNF search (including unsatisfiable sources) to a target requiring both output fault polarities, with recovery from every complete test set. This meets the fixed significance criterion once the two correctness defects are repaired. It adds one input and `O(m)` gates, designates one output wire, and serializes wire indices in `O(log(n+m))` bits each. Its target solver may still require exponential work and an explicit target answer contains `Θ(n)` test bits; no practical speed or throughput improvement has been shown. The source problem's openness was a request for reconstruction, not evidence of a new theorem.
